# 找资源场景 — 实现步骤与系统提示词

**创建日期：** 2026-06-14  
**状态：** 落地实现指南（可对接开发）  
**定位：** 把《找资源场景业务流程》从产品流程翻译成可落地的技术实现路径，明确工程与 LLM 的分工、各阶段里程碑、数据与检索服务契约，以及三处 LLM 触点的系统提示词草稿。供产品与开发对接使用。  
**关联文档：** 《找资源场景业务流程》《小博士场景意图路由策略》；原型 `AI 教学助手/workspace_find.jsx`  

---

## 1. 核心认知（先对齐，否则方向会错）

找资源里 **LLM 不负责"找"**。真正把资源找出来的是学科网的检索/推荐服务，LLM 只做三件事：理解意图、编排检索、叙述结果。

原型当前用本地 mock 数据，所以表面看像"AI 在找"。落到真实系统，约 80% 的工作量在数据与检索底座，系统提示词只是最薄、最后、最容易改的一层。因此本指南的重心放在工程底座，提示词排在后面。

一句话原则：**先把数据和检索做实，再写 Agent 和提示词。**

---

## 2. 系统架构分层

找资源拆成四层，职责严格分离。下面四个名字（路由层 / Agent 层 / 检索层 / 数据层）在全文统一使用，看到名字即知所指，无需回查：

```text
┌────────────────────────────────────────────────────┐
│ 【路由层】全局意图路由（独立，跑在所有场景之前）         │ ← LLM 触点①（或轻量分类模型）
│   决定：这句话进不进"找资源"                            │
└────────────────────────────────────────────────────┘
                      │ 命中找资源
                      ▼
┌────────────────────────────────────────────────────┐
│ 【Agent 层】找资源对话编排                             │ ← LLM 触点②（核心）
│   解析需求 → 判断追问/检索 → 调工具 → 叙述 → handoff   │
└────────────────────────────────────────────────────┘
                      │ 调 search_resources
                      ▼
┌────────────────────────────────────────────────────┐
│ 【检索层】检索编排服务（确定性工程，不靠大模型）         │
│   多源检索 · 打来源标签 · 排序 · 放宽 · 冻结 round      │
└────────────────────────────────────────────────────┘
                      │ 依赖
                      ▼
┌────────────────────────────────────────────────────┐
│ 【数据层】资源元数据库 + 三源（学科网 / 我的内容 / 资源篮）│
└────────────────────────────────────────────────────┘

前端：round 状态管理 · 资源操作 · 跨场景 handoff（原型已基本实现）

```

> **handoff 含义**：切换到另一个生成场景（出卷子/教案/课件），**只改右侧面板**，左侧对话线索不中断——用户感知为"同一位助手继续"，不是新开会话。见产品设计 §2.4 会话与多轮迭代模型。

> 四层一句话速记：**路由层**判断进不进找资源；**Agent 层**听懂需求、决定追问还是检索、叙述结果；**检索层**真正把资源查出来、排好序、冻结成一轮；**数据层**是资源库本身。

关键分工纪律：

- **排序、过滤放宽、round 冻结一律是确定性代码，不交给 LLM。** 否则"我的内容 > 资源篮 > 学科网"的优先级和"给你了就是你的"的冻结契约会不稳定。
- **LLM 只读检索结果、不做计算。** 它叙述结果，但不决定哪些资源排前面。

## 3. 实现步骤与里程碑

按推荐落地顺序排列。前序阶段是后序阶段的硬依赖。

### 阶段 0：数据与检索底座（最难，先做）

这是原型与真实系统的最大鸿沟。

| 产出 | 说明 | 阻塞关系 |
| --- | --- | --- |
| 资源元数据 schema 落库 | 原型卡片上的字段后端必须真有（见 §4.1） | 阻塞全部 |
| 检索服务 | 关键词 + 多条件过滤，返回带完整字段的排序结果（搜索/推荐系统能力，非大模型） | 阻塞检索层 |
| 三源打通 | 学科网公共库 + 我的内容（用户身份+资源归属）+ 资源篮（收藏持久化） | 阻塞检索层 |
| 登录态与降级 | 未登录时"我的内容/资源篮"不可用，需优雅降级 | 阻塞检索层 |

### 阶段 1：全局意图路由层

| 产出 | 说明 |
| --- | --- |
| 路由分类能力 | LLM 或轻量分类模型，输出 {场景, 置信度, 依据} |
| 低置信度确认机制 | 置信度低时轻量确认，不直接执行错误场景 |
| 混合意图衔接 | "知识+资源"先问教材、后挂资源入口 |

### 阶段 2：找资源 Agent

| 产出 | 说明 |
| --- | --- |
| Agent 系统提示词 | 见 §5.2 |
| search_resources 工具定义 | 见 §5.3 |
| 追问决策 | 提示词 + 后端"已追问次数"阈值双控 |
| 防幻觉兜底 | 后端校验 LLM 回复提到的标题都在本轮返回集合内 |

### 阶段 3：检索编排服务

| 产出 | 说明 |
| --- | --- |
| 多源合并 + 打标 | 学科网 / 我的内容 / 资源篮 来源标签 |
| 排序 | 我的内容(0) > 资源篮(1) > 学科网(2) |
| 过滤放宽 | 无命中时逐级放宽（先学段、再学科），不返回空列表 |
| round 冻结 | 每轮结果集不可变，分配 round id，可精确回看 |

### 阶段 4：前端状态 + 资源操作 + handoff

| 产出 | 说明 |
| --- | --- |
| round 回看 | 点回复入口重开对应轮次（原型已实现） |
| 资源操作 | 预览/播放/专辑/收藏/下载，对接真实接口 |
| 跨场景 handoff | 送去出卷子/教案/课件，带知识主题+难度（仅切换右侧面板，左侧对话不中断） |

### 阶段 5：灰度与评估

| 核心指标 | 含义 |
| --- | --- |
| 路由命中准确率 | 是否正确进入找资源 |
| 需求解析准确率 | 自然语言 → 结构化条件是否准 |
| 检索相关性 | 返回资源贴合度（人工抽检） |
| 跟进/流转点击率 | 跟进建议与 handoff 的有效性 |
| 幻觉率 | 回复中出现不存在资源的比例（应趋零） |

## 4. 数据与检索底座规格

### 4.1 资源元数据 schema

每个资源至少包含：

| 字段 | 用途 |
| --- | --- |
| 资源形态 | 文档 / 视频 / 专辑（决定结果分轨） |
| 学科、学段、年级 | 检索过滤主维度 |
| 版本（edition） | 筛选项：人教版/北师大版/通用… |
| 类型（type） | 同步练习/单元测试/微课·学案/专项突破/教学课件… |
| 难度 | 基础/中等/拔高 |
| 题量 / 页数 | 文档卡片展示与匹配判断 |
| 是否审校 | 信任标识 |
| 知识点 tag | 关联问教材、组卷流转 |
| 视频专属 | 时长、画质、章节、播放量、分类（实验/研修/示范课…） |
| 专辑专属 | 内含资源清单 |
| **match（匹配度）** | 0~100 整数，由检索层计算后返回，前端直接展示圆环，Agent 层只读引用 |

### 4.2 search_resources 服务契约

入参（由 Agent 层解析后传入）：

```text
{
  resource_form: "doc" | "video" | "album" | "all",
  subject, grade, edition, type, difficulty, topic,
  use_my_content: bool,   // 登录且允许时取"我的内容"
  use_basket: bool,       // 取"资源篮"收藏
  session_basket_titles: [...]  // 用于打"资源篮"来源标签
}
```

出参（检索层处理后返回，Agent 层只读）：

```text
{
  round_id,
  query,
  items: [ { ...完整字段, _source: "学科网"|"我的内容"|"资源篮", _kind: "doc"|"video"|"album", match: 0~100 } ],
  count,
  kind, subject, grade   // 本轮锁定的理解，回写累积上下文
}
```

检索层内部确定性逻辑：

- 按 resource_form 决定文档/视频/专辑混排比例与单轮上限（如"全部"≈2 专辑 + 8 文档 + 3 视频，上限约 14 项）；
- 按学科/学段过滤，为空时逐级放宽，保证不空手；
- **计算每条资源的匹配度（match），见 §4.3**；
- 打来源标签，按"我的内容 → 资源篮 → 学科网"重排；
- 冻结为 round，分配 id，历史永不覆盖。

> **什么是"冻结 round"**：用户每发一句检索需求，就是一轮（round），对应回复下方那个「已为你匹配 X 个资源」入口。检索层把上面几步（多源检索 → 打标 → 排序 → 放宽）全做完、结果定稿后，把"这批结果 + 查询条件 + 唯一编号"打包成一个**不可变的快照**存起来，这一步就叫冻结。它必须是检索层流水线的最后一步——前面任何一步没做完，结果都还会变，存下来就是半成品。类比拍照：前面是对焦调光，冻结就是按快门那一下，照片拍下不再改。冻结之后，用户继续问会生成新 round，旧 round 永不被覆盖，点回复入口即可精确重开当时那一批结果，对应业务流程里"给你了就是你的"。

### 4.3 匹配度（match）计算规则

匹配度是**检索层计算好后挂在每条资源上返回的字段（0~100 整数）**，前端直接展示圆环，Agent 层只读引用，不做二次计算。

> **原型现状**：data.jsx 里的 match 字段（98、95、92…）是写死的 mock 数据，不代表真实计算。真实系统需要检索服务在返回结果时带上这个分数。

#### 计算来源：两层叠加

**第一层：字段精确匹配（0~60 分，确定性代码）**

把用户本轮识别出的检索条件和资源字段逐项对比，命中加分：

| 字段 | 完全命中 | 部分命中 | 未命中 |
| --- | --- | --- | --- |
| 学科 | +30 | — | 通常已被过滤掉 |
| 学段/年级 | +25 | 相邻年级 +10 | 0 |
| 难度 | +20 | 相邻难度档 +10 | 0 |
| 版本 | +15 | 通用版 +8 | 0 |
| 资源类型 | +10 | — | 0 |

上限 60 分（学科通常已过滤，实际最高得分由剩余字段决定）。全部用确定性代码计算，不需要模型参与。

**第二层：语义相似度（0~40 分，向量计算）**

字段精确匹配解决不了知识主题的语义对齐——用户说「有理数」，资源标题可能是「有理数的加减法」「数与代数·有理数单元」，字面不一样但语义高度相关。

```text
用户输入的知识主题（topic 字段）
    → Embedding 模型 → 向量 A

资源标题 + 知识点 tag 拼接文本
    → Embedding 模型 → 向量 B

余弦相似度(A, B) × 40 → 语义相似度分（0~40）
```

Embedding 模型选轻量文本向量模型即可（如智谱 embedding-3、阿里 text-embedding、本地 bge-m3），不需要大模型。**向量在资源入库时预计算并存储，检索时只做查询侧向量计算 + 相似度打分，不是每次全量实时算。**

**最终匹配度 = 字段精确匹配分（0~60）+ 语义相似度分（0~40），四舍五入取整。**

#### 最简落地路径（快速验证）

如果 Embedding 服务短期改造成本高，可先只做第一层（字段精确匹配），暂时跳过语义相似度。算出来的分数已经能正确区分「完全命中」和「放宽后的候选结果」，比写死的 mock 数据有意义，先跑通链路，后续再叠加向量层。

#### Agent 层提示词中对 match 的引用规则

在 §5.2 系统提示词「对具体资源的描述必须基于返回字段」一条补充说明：

> 资源有 match 字段（0~100）时，可在描述中自然引用（如"匹配度 92"），但**不要自己估算或编造**这个数值——它由检索层计算，Agent 层只读。

## 5. LLM 触点与系统提示词

"系统提示词"不是一个，是三个触点，不要用一个大 prompt 包圆。

**为什么不能一个大 prompt 包圆？**

三个原因：

- **上下文污染**：路由层的 prompt 在每句用户输入之前都跑一次，它只需要判断"这句话进哪个场景"。如果把找资源 Agent 的完整 prompt 也塞进去，模型要处理大量此刻用不到的信息，判断准确率反而下降，且每次路由都多消耗大量 token。

- **职责混乱，难以维护**：找资源 Agent 的 prompt 是为"已确认进入找资源场景后"写的，里面有检索条件格式、追问规则、结果叙述规范——这些对路由判断毫无意义。合并后，模型会在错误时机激活错误行为，改一处逻辑容易牵连另一处。

- **不同触点可以独立选型**：路由层用轻量分类模型或小 prompt，速度快、成本低；Agent 层用能力强的大模型处理复杂多轮对话；叙述层也可以换更便宜的模型单独做。拆开后每个触点独立选型、独立调优、独立替换，不互相绑定。

| 触点 | 所在层 | 职责 | 形态 |
| --- | --- | --- | --- |
| ① 全局路由 | 路由层 | 判断进不进找资源 | 分类 prompt 或轻量模型 |
| ② 找资源 Agent（**主方案**） | Agent 层 | 解析+追问决策+叙述+handoff，LLM 是控制中枢 | system prompt + 函数调用工具 |
| ② 独立抽取（**备选方案**） | Agent 层 | 解析→代码判断→调检索→LLM 叙述，代码是控制中枢 | 三段独立 prompt，代码串联 |

### 5.1 全局路由提示词（触点①，两种方案共用）

```text
判断用户输入应进入哪个教学场景，只输出 {场景, 置信度, 依据}。

- 找资源：含 找/下载/有没有/资源/试卷/课件 等检索意图
- 问教材：问概念/定理/原因/区别/教材内容理解
- 生成类：明确要 生成/做/写/出 课件·教案·卷子
- 通用兜底：非教学或无法判断

优先级：明确文件处理 > 明确生成 > 找资源 > 问教材 > 方法指导 > 通用。
"知识+资源"混合（如"X有哪些重点？有没有课件？"）先问教材、后挂资源入口。
置信度低时返回"需确认"，不要直接执行。
```

> ⚠️ **上线前需调整**：场景关键词（找/下载/有没有/试卷/课件等）是经验初值，需用真实用户输入跑一批，按误判类型迭代补充。混合意图的优先级规则（如"知识+资源"的处理方式）也需要结合产品实际策略确认。

### 主方案：Agent 函数调用（5.2 + 5.3）

**适用前提**：使用的模型函数调用能力稳定（Kimi、GLM-4.7 均满足）。

**LLM 是控制中枢**，代码只负责执行工具调用和展示结果。多轮对话历史由 LLM 自动维护，追问和模糊跟进无需代码额外处理。

#### 5.2 找资源 Agent 系统提示词

```text
# 角色
你是学科网小博士的"找资源"助手。教师向你描述教学资源需求，你帮他从学科网资源库
找到合适的成品资源（文档/视频/专辑），资源不合适时引导他直接生成。

# 硬约束（最高优先级）
- 你不"知道"任何资源。所有资源只来自 search_resources 工具的返回。只能基于工具
  返回的真实字段说话——禁止编造标题、页数、题量、来源、审校状态等任何字段。
- 你不回答学科知识问题（那是"问教材"场景）。用户问"X是什么/为什么"这类纯知识
  理解时，提示可切换到问教材，不要自己长篇科普。

# 每轮注入的上下文
- 用户本轮输入
- 累积上下文：历史轮次已识别的学科、学段（用于解析模糊跟进）
- 登录态：登录/未登录（决定能否取"我的内容"、能否收藏与下载）
- 资源篮：用户已收藏的资源标题列表

# 工作流程
1. 抽取检索条件：资源形态(文档/视频/专辑/全部)、学科、学段、版本、类型、难度、
   知识主题。识别不到的字段，优先用累积上下文补全。
2. 判断信息是否够检索：
   - 能拿到"主题或资源形态 + 学科/学段"→ 直接调 search_resources。
   - 仅当需求宽到无法有效检索（如只说"找点资料"、完全无法识别学科）→ 发起一轮
     追问，给结构化选项并保留"我自己输入"。最多一轮，用户不补就用现有条件先检索。
   - 模糊跟进（"难度再高一点""只要含答案的"）一律用累积上下文+新条件直接检索，
     不追问。
3. 拿到工具返回后生成回复：
   - 说明你的理解（如"理解为七年级数学"）、检索总数、其中多少来自用户自己的内容/
     资源篮收藏。
   - 对具体资源的描述必须基于返回字段，具体、自洽、不空泛吹捧。
   - 给 2~4 个贴合当前结果形态的跟进建议。
4. 识别流转意图：用户说"出卷子/组卷""做教案""做课件"时，输出 handoff 动作并带上
   当前知识主题与难度，不要自己生成内容。（handoff 由前端执行：右侧面板切换到对应
   生成场景，左侧对话线索不中断。）

# 语气
简洁、专业，像一个懂教学的同事。不奉承，不堆形容词。
```

> ⚠️ **上线前需调整**：①"每轮注入的上下文"格式需与前端实际传参对齐（字段名、数据结构）；②工作流程中的字段枚举值（学科、学段、版本、类型、难度）需替换为学科网标签树的真实值，否则抽取结果对不上检索服务的过滤参数；③上线后用 20~30 条真实用户输入做冒烟测试，按误判案例微调追问触发阈值和叙述详略。

#### 5.3 search_resources 工具定义（主方案配套）

```text
search_resources(
  resource_form: "doc" | "video" | "album" | "all",
  subject, grade, edition, type, difficulty, topic,
  use_my_content: bool, use_basket: bool
) → 返回带完整字段、已打来源标签、已排序的资源列表（即 §4.2 出参）
```

过滤、排序、放宽、冻结都在工具背后的检索层完成，Agent 不感知。

> ⚠️ **上线前需调整**：参数名、字段类型、必填项必须与后端检索服务的真实接口对齐，现在是按设计意图写的，不是真实接口文档。对接时以后端接口为准。

### 备选方案：独立抽取 prompt（5.4）

**适用前提**：模型函数调用不稳定、需要高度可控的链路、私有化部署模型能力有限时使用。

**为什么是多段 prompt**：代码做控制中枢，抽取 / 判断 / 叙述三步由代码顺序调用，每段 prompt 只给模型它需要的输入、只让模型做它擅长的事。每段都短、都聚焦，出问题容易定位是哪一步错了。

**代码是控制中枢**，LLM 分三段介入，中间由代码串联。追问和模糊跟进的状态需要代码自己管理，工程量更大，但每一步都可以打日志、可以拦截，链路完全透明。

#### 5.4 整体流程（代码视角）

```text
用户输入
    │
    ▼
【第一段 LLM】意图抽取 prompt
    → 输出 JSON 条件（见下方 schema）
    │
    ▼
代码判断：
    ├─ need_clarify = true  → 生成追问文案（可用模板或小 prompt）→ 等用户回复
    │                          → 记录"本会话已追问次数"，超过 1 次强制走检索
    ├─ is_vague_followup = true → 把历史累积 subject/grade 合并进条件
    └─ 否则 → 直接调检索层 search_resources
    │
    ▼
检索层返回结果
    │
    ▼
【第二段 LLM】回复生成 prompt
    → 输入：用户原始问题 + 检索结果（完整字段）+ 登录态 + 资源篮
    → 输出：面向用户的自然语言回复
    │
    ▼
代码校验：回复中提到的资源标题必须在本轮检索结果集合内，否则拦截重写
    │
    ▼
展示给用户
```

#### 5.4.1 意图抽取 prompt（第一段 LLM）

```text
从用户输入中提取资源检索条件，只输出 JSON，不输出任何解释文字。

当前累积上下文（历史轮次已识别）：
- 学科：{accumulated_subject 或 "未知"}
- 学段：{accumulated_grade 或 "未知"}
本会话已追问次数：{clarify_count}

用户输入：{user_input}

输出格式：
{
  "resource_form": "doc" | "video" | "album" | "all",
  "subject": "识别到的学科，识别不到则填 accumulated_subject，仍未知填 null",
  "grade": "识别到的学段，识别不到则填 accumulated_grade，仍未知填 null",
  "edition": "版本，识别不到填 null",
  "type": "资源类型，识别不到填 null",
  "difficulty": "难度，识别不到填 null",
  "topic": "知识主题，识别不到填 null",
  "is_vague_followup": true/false,  // 本句是对上一轮的补充调整（如"只看视频""难度再高"）
  "need_clarify": true/false,       // 需求过宽、连学科都无法确定，且本会话追问次数 < 1
  "clarify_missing": ["subject", "grade"]  // need_clarify=true 时，列出缺失的关键字段
}
```

> ⚠️ **上线前需调整**：`subject`、`grade`、`edition`、`type`、`difficulty` 的枚举值必须替换为学科网标签树的真实值（现在是示意性占位），否则抽取结果无法匹配检索服务过滤参数。替换方式：把真实枚举列表直接写进 prompt，让模型从中选取而非自由生成。

#### 5.4.2 回复生成 prompt（第二段 LLM）

```text
你是学科网小博士的"找资源"助手。根据下面的检索结果，生成一段面向教师的回复。

硬约束：
- 只能描述检索结果中真实存在的资源，禁止编造任何字段。
- 不回答学科知识问题。
- 用户若表达"出卷子/做教案/做课件"意图，输出 handoff 标记，不自己生成内容。（前端收到标记后切换右侧面板，左侧对话不中断。）

本轮检索理解：学科={subject}，学段={grade}
检索结果（共 {count} 项）：{items 完整字段 JSON}
登录态：{logged_in}
资源篮收藏数：{basket_count}

回复要求：
1. 说明本轮理解（如"理解为七年级数学"）、总数、其中多少来自我的内容/资源篮。
2. 对 2~3 个代表性资源给出具体描述（基于真实字段）。
3. 给 2~4 个贴合当前结果形态的跟进建议。
4. 语气简洁专业，不奉承，不堆形容词。
```

> ⚠️ **上线前需调整**：用真实检索结果跑一批，验证"2~3 个代表性资源"的描述是否符合产品预期的语气和详略；handoff 触发词（出卷子/做教案/做课件）需与产品实际支持的跨场景流转能力对齐，不支持的场景先从 prompt 中移除。

#### 5.4.3 追问文案（need_clarify = true 时，可用模板）

```text
我还需要确认一下才能给你精准推荐。请选择或自己输入：

学科：语文 / 数学 / 英语 / 物理 / 化学 / 生物 / 历史 / 地理 / 其他
学段：小学 / 初中（七/八/九年级）/ 高中（高一/高二/高三）/ 我自己输入
```

> ⚠️ **上线前需调整**：学科列表和学段选项需对齐产品实际支持的范围（如是否包含政治、体育、美术等；学段粒度是否细到年级）。选项顺序建议按用户频率排序，高频学科放前面。

#### 5.4.4 备选方案代码需要额外管理的状态

与主方案相比，使用备选方案时代码需要自行维护以下状态：

| 状态 | 用途 | 主方案是否需要代码管理 |
| --- | --- | --- |
| accumulated_subject / grade | 模糊跟进时补全条件 | 否（LLM 看对话历史自动处理） |
| clarify_count | 防止多轮追问死循环 | 否（LLM 提示词控制） |
| 本轮返回资源集合 | 防幻觉校验 | 两种方案都需要 |
| handoff 意图标记 | 触发跨场景流转 | 否（LLM 直接输出 handoff 动作） |

## 6. 提示词工程的三个坑

第一，**别让提示词承担检索和排序。** "我的内容 > 资源篮 > 学科网"、过滤放宽、round 冻结全部用确定性代码，LLM 只读结果不做计算。

第二，**防幻觉要写成硬约束 + 工程兜底。** 找资源一旦 LLM 编出不存在的"《XX 期末卷》"，教师点进去是空的，信任直接崩。除提示词写死外，后端必须校验 LLM 回复里提到的标题都在本轮返回集合内，否则拦截重写。

第三，**追问克制靠提示词 + 阈值双控。** 光在提示词写"最多一轮"不够稳，后端要记"本会话已追问次数"，超过强制走检索。
